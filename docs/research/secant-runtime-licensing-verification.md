# Verify Secant's runtime and proprietary-distribution constraints

Checked 2026-10-07. Research only. No source, release, license, or provider configuration changed. The downloaded executables were read as data and never run.

## Confirmed conclusions

Secant can have a private development repository and free proprietary application downloads. Existing MIT grants and embedded third-party terms survive that change. The current runtime inventory does not cover Bun's complete native dependency closure. That gap is confirmed against Bun 1.4.2, its pinned dependency source, and the actual released archives. A completed legal-compliance certification would require a selected distribution/remedy and final license terms, neither of which exists yet.

The released Linux executable exposes readable transpiled Secant JavaScript. This is directly observed, rather than inferred from a compiler manual. Keeping the repository private does not hide code already shipped in this executable.

## Exact Bun and native dependency evidence

Bun's `bun-v1.4.2` tag resolves to commit `744846f844374847c902b5e7fd59b4342a51ef99`. Secant pins `bun@1.4.2` in `package.json`; its release inventory and shipped notices state this runtime version. The tag metadata and official source were downloaded through the GitHub API. [Bun tag](https://github.com/oven-sh/bun/tree/bun-v1.4.2), [tag API](https://api.github.com/repos/oven-sh/bun/git/refs/tags/bun-v1.4.2).

Bun's exact-version license file states that Bun's own code uses MIT, JavaScriptCore/WebKit uses LGPL, and the runtime statically links numerous native libraries. Its notices identify TinyCC under LGPL 2.1, plus libraries under BSD, Apache, zlib, ICU, MIT and other terms. The runtime's own MIT label cannot substitute for these component licenses. [Bun 1.4.2 license](https://github.com/oven-sh/bun/blob/bun-v1.4.2/LICENSE.md).

The exact-version WebKit build definition pins `2e2aa2290fac856d6f451ceacb58f7f5b44dd057`, links JavaScriptCore and WTF, and enables static JSC. Linux and Windows prebuilts also include ICU; macOS uses system ICU. [Pinned WebKit build](https://github.com/oven-sh/bun/blob/bun-v1.4.2/scripts/build/deps/webkit.ts).

The pinned engine contains actual LGPL-covered implementation files. `Source/JavaScriptCore/runtime/JSString.cpp` and `JSObject.cpp` carry GNU Library GPL version 2-or-later notices. This settles the concern that only obsolete unused engine material might carry LGPL. It also avoids incorrectly labelling all modern WebKit files LGPL; the project has mixed per-file licensing. [Pinned JSString implementation](https://github.com/oven-sh/WebKit/blob/2e2aa2290fac856d6f451ceacb58f7f5b44dd057/Source/JavaScriptCore/runtime/JSString.cpp), [pinned JSObject implementation](https://github.com/oven-sh/WebKit/blob/2e2aa2290fac856d6f451ceacb58f7f5b44dd057/Source/JavaScriptCore/runtime/JSObject.cpp).

TinyCC is pinned to `05f0fafaa3be31e31d7b4b5c17dc60f62c991171` in `oven-sh/tinycc`. Bun applies `patches/tinycc/tcc.h.patch`, builds platform-specific sources into a static archive, and includes the dependency in the final native build. Configuration excludes TinyCC only on Android and FreeBSD by default. All three Secant release targets are therefore enabled. TinyCC's pinned `COPYING` contains LGPL 2.1. This proves the upstream target/build contract, not a byte-by-byte symbol audit of every released platform runtime. [TinyCC build](https://github.com/oven-sh/bun/blob/bun-v1.4.2/scripts/build/deps/tinycc.ts), [target configuration](https://github.com/oven-sh/bun/blob/bun-v1.4.2/scripts/build/config.ts), [dependency link order](https://github.com/oven-sh/bun/blob/bun-v1.4.2/scripts/build/deps/index.ts), [exact TinyCC license](https://github.com/oven-sh/tinycc/blob/05f0fafaa3be31e31d7b4b5c17dc60f62c991171/COPYING).

Other native libraries also need version-specific notices. For example, Bun pins BoringSSL `41bf9b59c2ebf277a7aa427e1ecad5cc80dd4d4f` and libarchive `ded82291ab41d5e355831b96b0e1ff49e24d8939`, each with multiple applicable copyright/license texts. The current investigation confirms that they are separate native dependencies; it does not claim to have exhaustively mapped every compiled native source file to its license. [BoringSSL build pin](https://github.com/oven-sh/bun/blob/bun-v1.4.2/scripts/build/deps/boringssl.ts), [libarchive build pin](https://github.com/oven-sh/bun/blob/bun-v1.4.2/scripts/build/deps/libarchive.ts).

## What is missing from the present legal gate

`scripts/inventory.ts:165` creates fixed component entries for Bun under MIT and vendored OpenCode under MIT. Its other components come from the bundled npm graph. That does not inspect Bun's native C/C++/Rust dependency graph.

`THIRD-PARTY-NOTICES.md:561` identifies Bun MIT and mentions upstream terms generically. It contains no GNU Library/Lesser GPL license text, no TinyCC component attribution, and no exact runtime-source/relinking instructions. The notices extracted from each v0.1.0 release archive have that same gap. All three archives contain only the executable, `LICENSE`, and `THIRD-PARTY-NOTICES.md`; none includes an additional native-license or relinking kit. These observations are confirmed package contents, rather than assumptions about a future proprietary release.

A passing legal-closure check proves the checks it implements: npm inventory coverage and identical legal-material hashes across channels. It cannot establish full native runtime compliance. This gap already exists in the MIT release; making the first-party application proprietary changes the proposed application terms, not whether third-party licenses apply.

A follow-up checked whether Bun might supply the missing native notices inside the executable itself. The actual Linux artifact contains no plaintext matches for `GNU LESSER GENERAL PUBLIC LICENSE`, `GNU LIBRARY GENERAL PUBLIC LICENSE`, `LGPL`, `COPYING.LIB`, or `--license`. Bun 1.4.2's main CLI dispatch and argument table expose no native-runtime-license command. `BUN_BE_BUN` bypasses the standalone application and enters Bun's normal CLI; it is not a notice command. `bun pm licenses` loads the caller's lockfile and installed `node_modules`, then groups npm package metadata by license. It does not emit Bun's embedded native license texts. These source checks and the binary scan provide no evidence of an accessible native-notice feature. A raw text scan cannot prove that no encoded/compressed representation exists anywhere in a binary. The confirmed claim is therefore that the shipped notices file and current inventory omit the native closure; this investigation does not declare the entire historical release legally noncompliant. [Pinned CLI dispatch](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/runtime/cli/mod.rs), [pinned argument table](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/runtime/cli/Arguments.rs), [npm license command implementation](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/runtime/cli/pm_licenses_command.rs).

## What LGPL permits and requires

The exact pinned JavaScriptCore `COPYING.LIB` contains GNU Library GPL version 2. Section 6 allows distributing the combined work under chosen terms, provided the recipient can modify it for their own use and reverse-engineer for debugging those changes. It requires notices and a copy of the license. One route supplies corresponding library source, including changes, plus the application in object and/or source form sufficient to relink with a modified library. Required data and utilities must also be available. Other routes include a qualifying written offer lasting at least three years or equivalent download access to those materials. Therefore a proprietary application is possible; original Secant TypeScript publication does not follow automatically from this clause. Merely linking to an upstream homepage is not proof that all required materials and rights have been supplied. TinyCC's LGPL 2.1 needs its own matching treatment. This paragraph is an interpretation of the operative license text, not a legal opinion on an unselected final artifact. [Pinned JavaScriptCore license, sections 4–6](https://github.com/oven-sh/WebKit/blob/2e2aa2290fac856d6f451ceacb58f7f5b44dd057/Source/JavaScriptCore/COPYING.LIB), [pinned TinyCC license](https://github.com/oven-sh/tinycc/blob/05f0fafaa3be31e31d7b4b5c17dc60f62c991171/COPYING).

## A concrete remedy to validate

The route with least product disruption is a public companion compliance kit for each release. It would contain complete native notices, exact Bun and patched native sources/build recipes, and the application representation and tooling needed to rebuild a working executable with a modified runtime. The original development TypeScript can remain private if the supplied representation satisfies the applicable terms.

Bun documents rebuilding against its patched WebKit through a local WebKit checkout, synchronizing the pinned source, and `bun run build:local`. That confirms an upstream rebuild mechanism exists. It does not prove that Secant's existing packages already give recipients everything needed. [Bun 1.4.2 contribution/build instructions](https://github.com/oven-sh/bun/blob/bun-v1.4.2/CONTRIBUTING.md#building-webkit-javascriptcore).

The exact-version executable documentation exposes `compile.executablePath`, which selects a custom Bun runtime binary. Source `target_executable` honors that override, and the injector writes the application module graph into the native executable. This supplies a plausible mechanism for reusing a bundled application with a user-built runtime. A first implementation can publish the emitted JavaScript/assets and a small build driver using that override, while retaining original TypeScript privately. [Bun 1.4.2 executable API](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/bundler/executables.mdx), [runtime selection and graph injection](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/standalone_graph/StandaloneModuleGraph.rs).

Acceptance must demonstrate an actual user-modified JSC/TinyCC build and successful Secant reassembly/run on each supported target, along with source, notices, utility completeness and a compatible EULA. No such roundtrip was executed in this investigation, so the companion-kit remedy remains a proposal to validate, not a certified finished remedy. Another option is a separate replaceable runtime/application distribution, which changes packaging and the single-file architecture decision. An alternative runtime would require a separate compatibility investigation.

## Direct inspection of source recoverability

The independently hash-verified released Linux executable is 116,205,024 bytes and has SHA-256 `5887fcd386d3e4a8f6ca1e13f0848feafc1d66be08faf7685ca4b33db9b74712`. A bounded static parser read its ELF `.bun` section using the exact-version Bun struct definitions. The graph is 34,893,048 bytes and describes 52 embedded modules/assets. Every module entry has zero application-bytecode and zero sourcemap bytes. Application chunks contain readable JavaScript, including original module path comments such as `// src/application/problems.ts` and function `pathNotFound`. Embedded migrations, WebAssembly parsers, OpenTUI native libraries and a built-in Workflow Bundle are also visible. The script never executes the binary or imported modules.

The repeatable [static ELF inspector](./secant-linux-bundle-inspect.py) reads the binary as data. Run it with Python and the extracted Linux executable path. The detailed module results were retained locally; the verified artifact identity and structural observations are recorded above. The extracted data is temporary audit material. Production code was untouched.

This does not reconstruct complete original TypeScript, types, comments, Git history or development tests. It proves that repository privacy and the present compilation settings do not hide shipped application JavaScript. Bun also states explicitly that bytecode does not obscure source, so adding bytecode would not settle the confidentiality question. [Exact-version bytecode documentation](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/bundler/executables.mdx#bytecode-compilation).

## Historical rights, contributors and npm metadata

The checked v0.1.0 tag carries MIT and a 2026 DevFlow-HQ copyright notice. MIT allows use, modification, distribution, sublicensing and sale with its notice preserved. Treat those historical grants as surviving a repository visibility change. MIT does not require making application source publicly downloadable. Preserving the old artifacts unchanged is compatible with adding dated supplemental compliance materials alongside them. [Historical Secant license](https://github.com/secantdev/secant/blob/v0.1.0/LICENSE), [MIT license](https://choosealicense.com/licenses/mit/).

Available local Git history has two author identities, `rohan` and `Rohan Garg`, with 722 and 19 HEAD commits respectively. Their names suggest one person, but a Git author identity is not proof of legal identity, employment rights or assignment. The inspected contribution guide has no assignment or CLA provision. No agreement file was found in the tracked filename search. This narrows the observable contributor question; it cannot confirm agreements held outside the repository. GitHub's terms preserve creator ownership and ordinarily license contributions under the repository license, with separate agreements taking precedence. MIT contributions can remain in a proprietary larger product while their notices survive. [GitHub terms, D.3 and D.6](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service#d-user-generated-content).

For future public packages under custom free-use terms, npm documents `SEE LICENSE IN LICENSE` with an included license file. It defines `UNLICENSED` for a private/unpublished package where the author does not grant others use rights. The existing root/platform/launcher MIT fields must match the chosen future license rather than carrying a misleading open-source label. This metadata syntax is confirmed; the new EULA is not drafted or reviewed, so no final proprietary-license compliance can be asserted. [npm package license metadata](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#license).

Trademark ownership and off-repository assignments are not verifiable from this audit. A source-visibility switch cannot establish them. They are owner/legal evidence questions, not unresolved Bun or npm documentation facts.

## Remaining work precisely

- Final free-use proprietary license terms, including required third-party rights carve-outs, must be selected and checked.
- The native component notice/source closure must be completed for the exact runtime and all targets.
- A public runtime replacement/relink kit must pass a real modified-runtime roundtrip before it is described as compliant.
- The owner must establish any off-repository employment, assignment or trademark facts they intend to rely on.
