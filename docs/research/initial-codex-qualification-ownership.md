# Initial Codex qualification cleanup ownership

Research for [Research: Who owns incomplete initial Codex qualification through shutdown?](https://github.com/secantdev/secant/issues/400).
This report is advisory. The approved audit disposition commissions a scoped ownership decision and keeps it nonblocking for M9. It does not approve an owner, a registry, or an Interface change. [Approved audit disposition](https://github.com/secantdev/secant/issues/379#issuecomment-5987992776).

## Answer and decision status

The initial-prepare path loses its cleanup responsibility when Codex qualification fails with an unconfirmed reap. The private qualification result retains the acquired generation, but `CodexAdapter.prepare` returns only the failure. No caller receives a cleanup handle, and the Adapter has no final shutdown operation. This is a demonstrated ownership gap. It does not prove a Windows process leak, and it does not make independent concurrent prepares invalid. [Initial prepare](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L185-L267), [failed qualification](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L3016-L3065), [current Interface](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/harness.ts#L873-L889).

My recommendation is an invocation-lived Harness lifecycle, owned through composition, that retains each initial preparation until either confirmed disposal or exclusive successful handoff to its Prepared Harness. It needs a normalized final-close operation, admission closure, and per-prepare cancellation. The retained collection's implementation is private; naming the owner does not require a particular registry or class. This recommendation awaits a human decision.

The existing Interface cannot express final invocation cleanup of failed or in-flight preparations. An additive Adapter lifecycle is the most cohesive candidate; an opaque failed-result cleanup handle is a valid alternative with different caller costs. Process-level lifetime ownership is possible but requires a broader Process scope contract. The selected contract warrants an ADR amendment because it changes lifecycle ownership and rejects real alternatives. No ADR or production change is made here. The current architecture requires bounded mechanical cleanup and exactly one owner, while the module-design rule places each lifecycle invariant in one owning Module. [ADR 0022](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/docs/adr/0022-own-a-truthful-deep-harness-seam.md), [ADR 0025](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/docs/adr/0025-organize-target-code-around-owned-deep-modules.md), [module-design standard](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/docs/agents/module-design.md).

## Where responsibility disappears

1. `qualifyLive` acquires an `OwnedProcess` through that prepare's supplied Process and phase observer. `handshake` constructs a generation containing the process, runtime connection, and diagnostic capture. Authentication refusal and protocol failure both reach `failedQualification`. [Acquisition and handshake](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L451-L568).
2. `failedQualification` attempts bounded stdin close and diagnostic settlement. It preserves the original qualification category and aggregates useful causes. `cleanup-timeout` or `cleanup-error` additionally returns `unreaped: generation`; neither receipt proves final exit. [Failed qualification](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L3016-L3065), [Process close variants](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/process/process.ts#L528-L539).
3. Initial `prepare` strips `unreaped` from the public result. `HarnessAdapter` exposes only `prepare`, and failed `PrepareResult` carries only `failure`. The caller has no operation that can continue cleanup. A cause, phase fact, or child fact is evidence, not cleanup authority. [Initial result translation](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L235-L243), [Interface](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/harness.ts#L849-L889).
4. Replacement preparation forwards `unreaped` into the already-owned Prepared Harness. That Harness retains it and refuses replacement until a later cleanup establishes final exit. This is per-Prepared-Harness exclusion, not an Adapter-wide ban on independent prepares. [Replacement translation](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L307-L325), [replacement retention](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L742-L804).

`OwnedProcess.closeStdin` caches its first shutdown receipt, including a timeout or error. `closed()` returns the independent native close promise. The existing replacement path therefore retries with a bounded observation of `closed()` rather than assuming another `closeStdin` call performs a fresh reap. A stdin failure can also yield `cleanup-error` after native closure, so cleanup error alone does not establish whether the process still lives. [Cached receipt and independent observation](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/process/process.ts#L948-L962), [stdin error translation](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/process/process.ts#L1041-L1059), [bounded replacement observation](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L919-L999).

## Caller lifetimes and shutdown

Composition constructs the Harness Adapters once per `wireApplication`, retains them in its private Harness Registry, and uses them for catalog qualification and Run preparation. The Application sees only normalized registrations. A per-Run Process may be reconstructed for its observer scope; an injected Process may instead be shared. These are actual construction lifetimes, not a prescribed future registry design. [Adapter construction](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/harness-registry.ts#L46-L136), [Process scopes and wiring](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/wiring.ts#L228-L323).

Catalog qualification pairs successful prepare with `readDefaults` and immediate `PreparedHarness.close`. A failed prepare returns normalized unavailability immediately. Run preparation likewise returns a normalized failure to Application before it constructs an interactive driver. Only successful preparations enter the existing driver cleanup path. The logging wrapper also returns failed preparation unchanged. [Catalog qualification](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/harness-registry.ts#L170-L224), [Run path](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/wiring.ts#L424-L458), [logging wrapper](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/harness-log.ts#L61-L88).

Harness Catalog retains qualification promises separately from Run tracking. `Application.shutdown` drains held Run drivers and aborts active Run promises; it has no qualification drain. `PrepareOptions` has no cancellation signal. Consequently, closing a Projection or invalidating its result cannot cancel native preparation, and racing a timeout against preparation only bounds the caller's wait. It does not stop that preparation. [Qualification promises](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/application/harness-catalog.ts#L71-L119), [shutdown](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/application/application.ts#L4037-L4090), [prepare options](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/harness.ts#L849-L878).

The headless signal path calls Application shutdown before closing stores and re-raising the signal. Its ordinary `finally` closes only Run Group and Catalog. TUI exit drains Application before renderer teardown and store close, but renderer construction failure reaches store cleanup before that inner drain path exists. `runSecantInvocation` records completion; it does not own child cleanup. A final Harness lifecycle must be paired with the composition lifetime on every exit path, including normal headless completion and construction/render failures. [Headless lifecycle](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/main.ts#L36-L93), [TUI lifecycle](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/tui-runtime.ts#L120-L220), [invocation log wrapper](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/operational-log.ts#L280-L323).

## Ownership alternatives

### Invocation-lived Harness owner

Proposal: add a normalized terminal lifecycle operation to `HarnessAdapter`, or introduce an equally small Harness scope Interface with `prepare` and final close. Composition constructs and closes this owner once per Secant invocation. Before returning a failed result, the owner retains any unconfirmed generation. Before successful handoff, it owns in-flight acquisition. After successful handoff, only the Prepared Harness owns that generation.

This contains protocol connection and diagnostic lifetime where the Harness Module already understands them. Independent preparations retain separate Process, observer, cancellation, and generation facts. Failure in one preparation does not block another. The owner can cancel and drain pending acquisitions during final close without exposing native process details.

The cost is a real Harness Interface change and an explicit lifetime obligation for every caller and test Adapter. It also amends the present rule that an Adapter keeps only its qualification cache across prepares. This is the strongest objection to this option, not a reason to hide the new lifecycle in a private collection with no final caller. [Current cache-only rule](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/AGENTS.md#L64-L65), [current Adapter Interface](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/harness.ts#L873-L889).

### Opaque cleanup handle on failed preparation

Proposal: failed `PrepareResult` optionally carries one normalized resource handle with bounded cleanup and independent completion observation. Composition accepts sole responsibility before returning normalized unavailability, retains the handle while unresolved, and drains it at final invocation close. No PID, RPC, connection, or native generation crosses the Harness Interface.

This keeps preparations independent and preserves a cache-only Adapter. It makes the failure's retained resource explicit. Its cost is a second resource-result vocabulary and ownership acceptance in every path that normalizes failed prepare. It still needs invocation-wide prepare admission and flight tracking: a handle returned after shutdown took its final snapshot otherwise escapes cleanup. A callback named `retainCleanup` has the same semantic obligations and is also an Interface change, even if its types look smaller. [Failure normalization sites](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/harness-registry.ts#L170-L224), [Run normalization](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/wiring.ts#L424-L436).

### Process-level lifetime owner

Proposal: a Process scope retains every acquired owned process until independently confirmed closure, and offers final bounded scope shutdown. Harness qualification can fail without returning a cleanup handle because the Process scope remains reachable through composition.

This centralizes mechanical retention and can protect other owners from similar omissions. Its cost is broader ownership for all owned children, explicit scope lifetimes, and coordination with already-transferred Prepared Harnesses. Process can report mechanical shutdown, but Harness still owns protocol failure and diagnostic translation. The current Process Adapter has no terminal close or child-retention contract. Per-Run Process construction is deliberately stateless apart from observation, so adding this ownership requires changing construction and tracking rather than closing one assumed global Process instance. [Process Interface and construction](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/process/process.ts#L594-L652), [per-Run construction](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/wiring.ts#L247-L273).

## Minimum contract to decide

The names and exact type shape remain open. Whichever owner is selected needs the following semantics:

- Register an acquisition under one owner before an await can let shutdown miss it. Final close closes preparation admission before enumerating or draining work.
- Allow independent concurrent preparations. The cancellation of one prepare affects only its acquisition. A final owner close may cancel all acquisitions it still owns.
- Add a per-prepare abort signal or equivalent cancellation scope if prompt caller cancellation is required. A bounded wait alone is not cancellation.
- Choose a linearization point for cancellation versus successful handoff. Exactly one owner wins: cancellation retains the untransferred generation, or successful return transfers it exclusively to the Prepared Harness.
- Preserve typed qualification failure and its cause. Cleanup observations are separate evidence and cannot convert authentication refusal into a successful qualification.
- Observe independently confirmed `closed()` after a cached timeout/error receipt. Release ownership only when the observation proves the owned lifetime ended; a second timeout remains unresolved.
- Make final close bounded and idempotent. An unresolved resource yields truthful unclean evidence. The bound cannot prove that an unresponsive process died, and a clean report cannot be fabricated to make teardown finish.
- Preserve historical cleanup failure even after a later confirmed exit removes live retention. Historical evidence and current unresolved-resource state are different facts.
- Pair final cleanup with normal exit, signals, errors, and any failure after composition has acquired resources. Complete lifecycle reporting before its log and stores close.

These are proposed requirements, derived from the existing bounded-cleanup and one-owner rules, not a human-approved replacement contract. [ADR 0022 cleanup and ownership](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/docs/adr/0022-own-a-truthful-deep-harness-seam.md), [ADR 0025 failure-path ownership](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/docs/adr/0025-organize-target-code-around-owned-deep-modules.md), [current retry observation](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L919-L999).

Successful handoff needs a precise limit. An invocation-lived Adapter must not later reap a generation that its Prepared Harness owns. H3 concerns pre-handoff acquisitions; successful Prepared Harnesses remain under their existing cleanup owner. An adjacent concern remains: `PreparedHarness.close()` caches its report, and composition's Step driver records itself closed before awaiting that report. An unclean report therefore prevents this proposal from claiming final cleanup of every Harness resource. Changing post-handoff cleanup continuation would require a separately scoped decision or an explicit human expansion of this effort. [Prepared close](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/codex.ts#L877-L917), [Step close](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/wiring.ts#L558-L597).

## Conformance evidence required before implementation acceptance

Use the real Harness Adapter through the Process Interface for deterministic cases. Required behaviors include failed initial qualification plus cleanup timeout/error; independent later final exit; final close with no exit; shutdown racing prepare before acquisition registration; cancellation racing success; simultaneous independent prepares with different Process and observer scopes; a late failed result during shutdown; and successful handoff with exactly one cleanup owner. Exercise cached shutdown receipts separately from historical failure retention.

Through composition, cover catalog qualification without a Run, Run prepare failure, normal headless completion, headless signal, TUI quit, and a startup/render failure after wiring. These are conformance obligations for the proposed owner, not tests added by this research. They follow from the existing Adapter-through-Interface test policy and the actual lifecycle paths traced above. [Harness conformance policy](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/harness/AGENTS.md#L90-L112), [headless lifecycle](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/main.ts#L36-L93), [TUI lifecycle](https://github.com/secantdev/secant/blob/4292ab94298f5de4e506d2ee32930fe1cb2d2c0d/src/composition/tui-runtime.ts#L120-L220).
