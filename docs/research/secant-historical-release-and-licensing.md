# Secant historical-release and licensing transition

Verification update: [Closed-source transition verification](./secant-closed-source-verification.md) confirms the one-seat monthly checkout, replaces the short-sample monthly estimate with a complete census, verifies all historical artifact bytes, and records the native-runtime notice gap. Read that update before acting on the original research below.

Researched 2026-10-07 for [Establish the v0.1.0 and licensing transition constraints](https://github.com/secantdev/secant/issues/426). This is research and an advisory cutover sequence, not approval to change visibility, licensing, published bytes, or production configuration. The maintainer confirms that the source becomes private while binaries remain free to download anonymously.

## Findings that determine the cutover

Making the source repository private does not create a public download channel. Source files, installers, release pages, and attached binaries in that repository cease to be an anonymous distribution channel. Existing public forks remain public, and changing visibility does not undo historical MIT grants. Preserve v0.1.0 as the already released MIT version. Apply chosen proprietary terms only to subsequent releases while retaining historical and third-party notices.

The main additional risk is redistribution compliance for the embedded Bun runtime. Secant's existing inventory treats Bun as one MIT component, but Bun's official licensing documentation identifies native components under other terms, including LGPL. A passing existing legal-closure check does not establish that the complete runtime's notices and relinking obligations are satisfied. This needs a bounded audit before proprietary release, rather than an assumption that Secant must publish all its own source.

## Evidence and limits

The starting-context commit is `418625c4ebc7273e82a848e66a34ec5149abcc92`. The v0.1.0 tag points to `8b14357645b5a712c96c8bda24dfe596c9f9c2d6`. Provider docs were fetched through Context7, followed by official web sources for exact wording and licensing. Facts observed in repository code are separated below from legal interpretation and policy recommendations. This investigation did not download all large release assets, inspect every contributor's contractual rights, decompile the release, or prove full runtime license compliance.

Migration must download the assets, recompute the hashes, upload the same bytes, and verify fresh anonymous downloads against those hashes. Copy release notes and historical tag-to-source-commit provenance as metadata. Changing URLs need not change the artifact bytes. [Historical release](https://github.com/secantdev/secant/releases/tag/v0.1.0), [release REST metadata](https://api.github.com/repos/secantdev/secant/releases/tags/v0.1.0).

The archive and npm packers hash the `LICENSE` and `THIRD-PARTY-NOTICES.md` bytes. They reject legal-material disagreement with the assembled candidate. The platform packages carry the executable, license, and notices; the launcher carries launcher code and the same legal material. Replacing v0.1.0's MIT license with a proprietary license would change archive hashes and invalidate the already approved candidate. Rebuilding or repacking is not a migration. [Assembly](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/scripts/assemble.ts), [platform packer](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/scripts/pack.ts), [launcher packer](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/scripts/pack-launcher.ts).

npm identifies a package by its name and version. An already published name/version cannot be republished, even after unpublishing. Leave historical npm versions intact. A new license or packaging change requires a new version. Secant promotion already accepts an existing registry version only when its tarball bytes match the approved candidate. The registry remains independently public when the GitHub source repository becomes private. Confirm the actual registry versions and integrity values during migration; this sub-investigation did not establish the full current registry inventory. [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/), [promotion implementation](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/scripts/release-promote.ts).

## What repository privacy changes

GitHub says existing public forks detach into a separate network and remain public. Stars and watchers are erased during the visibility change. GitHub Free Pages sites are automatically unpublished, and some security features require additional private-repository licensing. None of these operations retracts downloaded copies, clones, or lawful historical forks. [Visibility consequences](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility).

GitHub release access follows repository read access. Therefore attached release assets in the newly private source repository cannot remain the anonymous install origin. Authenticated maintainers retain access, but shipping a maintainer token to installers would expose private access. This is an inference from repository permissions, not a private-download probe performed on production. [About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

The automatically generated `Source code (zip)` and `Source code (tar.gz)` links are repository snapshots, separate from the five attached assets. On a clean public distribution repository, those links describe only that repository's public installers and documentation. Never create the distribution repository by pushing private source history or copying a source tag and its reachable tree. GitHub archives derive from repository branches, tags, or commits; compression bytes can change independently of file contents. Preserve approved binary assets, not regenerated source archives, as the installation inputs. [Source archive behavior](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives).

Whether to retain a separate public archive of the old MIT source is a maintainer policy choice. MIT does not require providing source with binary redistribution. Keeping such an archive aids historical verification but preserves the original code publicly by design.

## Old installer links require an explicit compatibility decision

The README currently advertises `raw.githubusercontent.com/secantdev/secant/main/install.sh` and `main/install.ps1`. Both installers resolve binaries through `github.com/secantdev/secant/releases`; scripts already downloaded by users retain those hardcoded URLs. A website redirect fixes only URLs controlled by `secant.sh`. It cannot redirect GitHub's raw-file paths or change a cached script. [Current README](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/README.md), [POSIX installer](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/install.sh), [Windows installer](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/install.ps1).

Two viable policies have different consequences:

- Keep the source at `secantdev/secant`, make it private, and create a public distribution repository at another name. Preserve the existing tracker identity. Advertise the new domain commands before cutover and accept that historical GitHub installer commands and cached scripts stop downloading. Existing installed binaries are a separate matter; this research found installer download coupling, not a running-binary auto-update dependency.
- Rename the source to an internal private repository and create a fresh public distribution repository at `secantdev/secant`. Keep a `main` branch with both installer filenames and copy the versioned assets there. This can preserve old raw URLs and cached-script release paths, subject to anonymous acceptance checks. GitHub warns that reusing the old repository name stops rename redirects. Existing issue, PR, and source links then resolve against the new public repository or fail rather than following the private tracker. Update local remotes, automation, and internal references accordingly. [Repository rename consequences](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository).

I recommend preserving the source/tracker identity and accepting a clearly announced legacy-command cutoff unless maintaining cached scripts is a hard requirement. Website endpoints such as `/install` and `/install.ps1` become the durable public entry points. If old paths are mandatory, the same-slug public repository is a deliberate tracker-link tradeoff, not a harmless rename.

## Historical MIT rights and future proprietary terms

The v0.1.0 `LICENSE` grants use, modification, redistribution, sublicensing, and sale, subject to notice preservation. MIT permits distributing larger works under other terms without publishing source. Making the repository private changes access, not the text of copies already released. The operational conclusion is to treat historical compliant MIT recipients as retaining those rights; this is legal interpretation from the grant, not a claim that privacy can revoke it. [Historical LICENSE](https://github.com/secantdev/secant/blob/8b14357645b5a712c96c8bda24dfe596c9f9c2d6/LICENSE), [MIT terms and summary](https://choosealicense.com/licenses/mit/).

GitHub's terms say contributors retain ownership of their content and generally submit contributions under the repository's existing license unless a separate agreement overrides it. Repository administration does not establish copyright assignment. Review authorship, employment or contractor agreements, and any contributor agreements before claiming sole ownership. MIT contributions can generally be included in a proprietary larger work while preserving their notices. They do not become exclusively owned by the maintainer. [GitHub terms, sections D.3 and D.6](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service).

At the starting-context commit, three package-license fields say `MIT`: root `package.json`, platform manifests in `scripts/pack.ts`, and the launcher manifest in `scripts/pack-launcher.ts`. A future free-to-use proprietary binary license needs actual terms granting installation and use. For a custom license, npm documents `SEE LICENSE IN LICENSE`, with that file included. `UNLICENSED` describes granting no use rights for private or unpublished packages, so it is unsuitable as the sole explanation of anonymously downloadable free-use binaries. The private source root may also use `private: true` to prevent accidental root-package publication, while generated distribution packages remain publishable. This is a configuration choice to implement only after the license decision. [npm package metadata](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/).

Choose whether installer and launcher code remains MIT while the application becomes proprietary, or whether all new first-party distribution code uses the custom license. Keep third-party permissions explicit in either case. A single proprietary header must not imply ownership of OpenCode, OpenTUI, Bun, or other embedded dependencies.

## Audit the entire embedded runtime

The notices include MIT, ISC, Apache-2.0, BSD, and Blue Oak components. Preserve their text and applicable attribution, NOTICE, modification, and redistribution requirements. The license change does not retire the artifact-level legal gate. Its current npm-graph coverage and cross-channel digest checks are valuable. [Third-party notices](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/THIRD-PARTY-NOTICES.md), [inventory implementation](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/scripts/inventory.ts).

Bun's own documentation distinguishes its MIT code from statically linked JavaScriptCore/WebKit under LGPL-2 and other native libraries, including tinycc under LGPL v2.1. It discusses providing relinkable application objects and rebuilding Bun against its patched WebKit. Secant's `fixedMembers` currently records Bun as MIT and the notice text acknowledges upstream components without enumerating their full terms. Review the exact shipped Bun 1.4.2 binaries, native license texts, corresponding source availability, any relinking requirement, and restrictions in the proposed EULA. This finding does not establish that LGPL requires opening Secant's application source or that the current package is conclusively noncompliant. It establishes an unanswered redistribution obligation that the current graph-based inventory cannot prove away. [Bun licensing](https://bun.sh/docs/project/license).

Keep v0.1.0 bytes unchanged during that review. Any supplemental compliance material can be published alongside the historical artifact with a clear date and purpose rather than silently modifying its approved archive. The precise remedy depends on the audit.

## A compiled executable is not a source secrecy boundary

Both the starting-context build and v0.1.0 build set no `minify`, `bytecode`, or `sourcemap` option. Bun's documented defaults are no minification and no sourcemap. The inventory build separately enables external sourcemaps to discover package dependencies; those inventory maps are distinct from the production compiler settings. [Build implementation](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/scripts/build.ts), [Bun bundler defaults](https://bun.sh/docs/bundler).

Bun bundles application modules and its runtime into the executable. Its official docs explicitly say bytecode compilation does not obscure source code. They describe minification as size reduction and embedded sourcemaps as compressed error-location metadata. The archive containing only a binary and legal files therefore does not prove unrecoverable application logic. No extraction was performed here, so this report does not claim a complete original-TypeScript reconstruction. Keep private build maps, source inventories, test fixtures, and logs out of public uploads, but do not market compilation or bytecode as confidentiality. [Bun executable documentation](https://bun.sh/docs/bundler/executables).

WIPO distinguishes secrecy controls from trade-secret status: information must have value because it is secret, be restricted, and receive reasonable protective measures. Protection varies by jurisdiction and generally does not prevent independent development or permitted reverse engineering. Historical public code cannot be made previously undisclosed by flipping repository visibility. Free downloadable executables also distribute behavior and embedded data. A proprietary license and private development repository are achievable; robust secrecy for code delivered to users is a separate requirement. [WIPO trade secrets](https://www.wipo.int/en/web/trade-secrets).

## Preserve public support and useful provenance

The README, support matrix, contribution guide, issue tracker, and package `bugs` metadata currently lead to the source repository. Privacy removes their usefulness for anonymous users. Publish installation instructions, supported-platform claims, changelogs, legal terms, and a support route on the website or public distribution repository. Keep development guidance and internal wayfinding private. Do not mirror the whole issue history merely to preserve a bug-report form. [README](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/README.md), [package metadata](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/package.json).

GitHub private vulnerability reporting is available on public repositories. A public distribution/support repository can retain a confidential reporting route even with private source. Alternatively publish a monitored security email or form. An email address is a proposal until the maintainer provisions and monitors it. [GitHub private reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately).

Public packages necessarily expose package names, versions, dependency identities, license text, executable names, and whatever is shipped in binary assets. Current promotion uses public npm publication and does not explicitly request npm provenance. If provenance, attestations, signatures, or a public publisher workflow are introduced, review their metadata for private repository identity, commit hashes, build paths, and log content. Public verification metadata should still identify the exact approved bytes; hiding private source does not require hiding checksums or notices. [Promotion implementation](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/scripts/release-promote.ts).

ADR 0028 waived trademark and native-speaker checks partly because Secant was open source and had no registered company. The explicit revisit triggers are commercial offering, incorporation, trademark filing, exclusivity claims, or a conflict. Free proprietary distribution does not automatically meet every trigger, but its changed premise deserves a recorded review rather than silently carrying the waiver forward. Trademark status remains unknown. [ADR 0028](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/docs/adr/0028-adopt-secant-as-the-product-package-and-command-name.md), [release checklist](https://github.com/secantdev/secant/blob/418625c4ebc7273e82a848e66a34ec5149abcc92/docs/release-checklist.md).

## Recommended order after the maintainer resolves policy

1. Select the private repository identity, compatibility policy, public host, custom license, security/support home, and approved release-protection mechanism. Complete the rights and embedded-runtime audit.
2. Export v0.1.0 assets and evidence. Recompute and record hashes. Inventory actual published npm versions without removing or republishing them.
3. Provision a clean public distribution channel. Copy exact historical assets, keep historical MIT terms, and verify every asset through unauthenticated downloads on supported platforms.
4. Publish and verify `secant.sh/install` and `secant.sh/install.ps1`. Verify latest and pinned-version behavior, cached-script compatibility if promised, notices, checksums, and rollback. Announce the old-command cutoff if that policy was chosen.
5. Adapt private CI and public publication while preserving the existing three-OS and digest-bound human release gates. Validate cross-repository credentials without publishing source or changing v0.1.0.
6. Change source visibility only after the replacement channel works. If the same-slug compatibility policy was chosen, perform the rename and clean public-repository handover with an explicitly accepted outage window and tracker-reference updates.
7. Build the first new proprietary candidate once, under a new version and the selected terms. Run the canonical gates and artifact legal review, obtain approval for those exact digests, then publish them through the established anonymous channel.

Remaining policy decisions belong to [Decide Secant's private-source CI, public distribution and cutover policy](https://github.com/secantdev/secant/issues/427). The runtime audit may need a focused follow-up research ticket if its facts cannot be settled in that decision session.
