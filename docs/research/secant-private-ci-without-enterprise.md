# Private CI and release approval without Enterprise

Research date: 2026-10-09. This resolves [Establish whether free CI runners and a public publish step can replace Enterprise](https://github.com/secantdev/secant/issues/507). It builds on [Private-source CI and release approval](./secant-private-ci-and-release-approval.md) and [Enterprise billing verification](./secant-enterprise-billing-verification.md), and it changes no settings, buys nothing, and signs up for nothing. Every provider fact below was read on that provider's own page on 2026-10-09. **Observed** means read from a primary source or measured from Secant's own API data; **derived** means arithmetic on observed numbers; **inferred** means reasoning that no source states.

## Direct answers

1. **Post-M12 CI usage.** In the 25.06 hours after M12 closed (2026-10-08 06:28 UTC to 2026-10-09 07:31 UTC), 43 `Check` pushes (46 attempts) used **532 Linux, 798 Windows and 509 macOS minutes**, worth **$42.73** at list price (observed). That is **$0.994 per push**: Linux $0.074, Windows $0.186, macOS $0.734. macOS is 74% of the cost. A typical green `main` push took 12 Linux, 17 Windows and 11 macOS minutes (medians). At the observed rate of 41 pushes/day, a 30-day month would be about 1,236 pushes, **15,286 Linux + 22,929 Windows + 14,625 macOS minutes, about $1,228 at list price** (derived; one sprint day is a small sample). At 200 or 320 pushes/month the same per-push cost gives $199 or $318. Free's $12 credit covers about 12 full pushes, or about 160 if it is spent on Linux alone (derived).
2. **Runner providers.** Only three providers on the shortlist have a recurring free allowance usable by a private repository: **Sengi** (3,000 Linux minutes, no card), **Blacksmith** (3,000 Linux-equivalent units shared across OSs; 1 Windows minute = 2 units, 1 macOS minute = 20 units; no card), and **Ubicloud** (a $2.50 Linux credit, about 1,250 minutes; card required). **GetMac** gives 100 macOS minutes. Every provider attaches the same way: install a GitHub App, then change `runs-on:`. The workflow stays GitHub Actions. All except RunsOn and Cirun run the private source on the vendor's own machines. **Cirrus Runners is closed to new customers**, RunsOn has no macOS, and Latchkey's $5 plan covers one repository. **No combination covers the measured load at $0.** With macOS taken off per-push CI (the cadence #427 already chose), $0 covers about **145 pushes/month**. Windows runs out first: 1,500 Blacksmith minutes plus 1,200 from GitHub's credit (derived). At the observed rate, the cheapest combination is about **$113–184/month**: Linux on Sengi plus Ubicloud (~$13–22), Windows on Namespace Team ($100) or Blacksmith (~$162), and macOS only on tags and dispatches (GetMac free tier). It is about **$275–345** if macOS stays on every push via GetMac. At 320 pushes/month it is about $26 (or ~$93 with macOS on every push); at 200 pushes/month about $8 (or ~$42) (all derived).
3. **Public publish step: feasible.** A workflow in public `secantdev/secant-releases` can fetch a private run's artifacts. `actions/download-artifact` v8 takes `repository`, `run-id` and `github-token`, and fails on a digest mismatch by default. The workflow can re-check its own per-file SHA-256 against the candidate manifest, wait on a `release` environment with a required reviewer (free on public repositories), and publish npm-first and then its own GitHub release with its own `GITHUB_TOKEN` (`contents: write`). **Least-privilege credential:** a GitHub App installed only on `secantdev/secant`, with only `Actions: read`, minted per job by `actions/create-github-app-token` with `permission-actions: read`. Its key is held as an environment secret in the public repository. **npm:** trusted publishing (OIDC) from the public repo works on GitHub-hosted runners and gives provenance automatically, which a private repo cannot. Direct publishing with a granular token ends in January 2027. **Public logs:** any signed-in GitHub user can read them, and run titles and approval history are readable without signing in. `download-artifact` prints the source repository name, run id, artifact names, IDs, sizes and digests; nothing private leaks unless the workflow prints it. A quiet `gh api` download script avoids even those identifiers. **macOS:** `codesign --verify --deep --strict` on the cross-compiled Darwin binary can run **free** on `macos-latest` in the public repository (standard runners are free for public repositories; Free allows 5 concurrent macOS jobs). Running the private test suite there is a different matter: it would put source-derived output in public logs, and it strains GitHub's Actions terms.
4. **What Free gives a private repository: almost nothing for release safety.** A private repository on Free gets no environments at all, so no environment secrets, required reviewers, wait timers, deployment branch or tag rules, or admin-bypass control. It also gets no rulesets (branch, tag or push), no classic protected branches, no access to organization secrets, and no required workflows. Legacy tag protection no longer exists anywhere; tag rulesets replaced it. What remains is plain repository secrets (readable by every workflow on every branch), the default `GITHUB_TOKEN` read-only setting, and the 2,000-minute ($12) and 500 MB allowances. Secant's existing `noForcePush` ruleset and `release` environment (reviewer `Sandstorm831`, `v*` tag policy, no admin bypass) would stop applying when the repository goes private (inferred from the availability rules).

## 3. A public publish step in `secantdev/secant-releases`

`secantdev/secant-releases` does not exist yet (`GET /repos/secantdev/secant-releases` returned 404 on 2026-10-09).

**Fetching the candidate (observed).**

- [`actions/download-artifact`](https://github.com/actions/download-artifact) is at v8.0.2 (2026-10-07). Its inputs include `repository`, `run-id`, `github-token`, `pattern`, `merge-multiple` and `digest-mismatch` (default `error`). `github-token` "is required when downloading artifacts from a different repository or from a different workflow run". The README asks for a "token with actions:read permissions on target repo".
- The REST [Download an artifact](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact) endpoint accepts GitHub App installation tokens and fine-grained PATs with "Actions" repository permission (read).
- The action's digest is of the artifact zip, not of each binary inside (inferred from source). So the public job must still re-hash each file against `candidate-manifest.json`/`SHA256SUMS`, as `release-promote.ts` already does. upload-artifact v7's `archive: false` is an option.
- The same `Actions: read` token can read the private run and its jobs. The public job can therefore prove the source run is the `Check` workflow on the exact `v*` tag, with all three-OS jobs green, before it publishes. A public workflow cannot have a literal `needs:` edge to private jobs.

**Approval (observed).** Required reviewers, prevent self-review, wait timers, deployment tag policies and environment secrets are all available "in public repositories for all current GitHub plans" ([manage environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)). "A job cannot access environment secrets until one of the required reviewers approves it" ([reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)).

**Least-privilege credential.** GitHub recommends a GitHub App for cross-repository access: "the `GITHUB_TOKEN` can only access resources within the workflow's repository … you can use a GitHub App" ([docs](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow)). PATs "are intended to access GitHub resources on behalf of yourself".

The App would be installed only on `secantdev/secant`, with only `Actions: read` (plus the mandatory `Metadata: read`). [`actions/create-github-app-token`](https://github.com/actions/create-github-app-token) v3.2.0 then mints a token scoped with `repositories: secant` and `permission-actions: read`. That token expires in one hour, is masked, and is revoked in the post step. `Actions: read` exposes the private run's logs and artifacts but not repository contents (inferred from the permission model).

The fallback is a fine-grained PAT with `Actions: read` on the one repository. It is tied to the maintainer's account, expires in at most 366 days, and needs org approval unless an owner creates it.

The public release itself needs no cross-repository write. The public job's own `GITHUB_TOKEN` with `contents: write` can create the release and tag in `secant-releases` ([releases API](https://docs.github.com/en/rest/releases/releases)).

**Triggering (observed).**

- Option 1: a REST `workflow_dispatch` from the private side, which needs `Actions: write` on the public repo.
- Option 2: `repository_dispatch`, which needs `Contents: write`, more than a dispatcher should hold.
- Option 3: the maintainer dispatches the public workflow manually with only the version. The workflow then finds the private run itself through the App token. This keeps the private side free of any credential for the public repository.

**npm (observed).**

- Requirements: [trusted publishing](https://docs.npmjs.com/trusted-publishers) needs npm CLI 11.5.1+ and Node 22.14+. It supports "GitHub Actions (GitHub-hosted runners)"; "Self-hosted runners are not currently supported".
- Configuration: each package names the organization, repository, workflow filename and an optional environment. `repository.url` in `package.json` "must exactly match your GitHub repository", so it would name `secant-releases` (inferred). A new trusted-publisher configuration must publish successfully within 2 days.
- Provenance: it is automatic when publishing from a public repository, and "not supported for private repositories, even when publishing public packages".
- Tokens: per [access tokens](https://docs.npmjs.com/about-access-tokens), "The ability to publish new package versions directly with a granular access token will be removed in January 2027". Today's `NPM_PUBLISH_TOKEN` path therefore has a deadline wherever promotion runs.
- Where the publish job can run: it must stay on a GitHub-hosted runner, which is free in a public repository.

**What appears in public logs (observed).**

- **Who can read what.** "You must be logged in to a GitHub account to view workflow run information, including for public repositories" ([logs](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs)), and any signed-in user can then read them. Run titles, `head_sha`, job and step names, deployments and approval history (reviewer and comment) are readable without signing in (probe and REST docs). Artifacts in a public repository can be downloaded by any signed-in user, so the public workflow must never re-upload an unapproved candidate as an artifact or draft asset.
- **What `download-artifact` prints.** It echoes its `with:` block, including `repository` and `run-id`. It logs "Downloading artifact '<id>' from '<owner>/<repo>'", each artifact's name, ID, size and expected digest, and the blob host with the query string scrubbed. The token prints as `***`.
- **Masking.** Secrets are masked by exact match. Derived or structured values are not guaranteed to be masked; GitHub's guidance is to register them with `::add-mask::` ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)).
- **What could leak.** None of this is source. What leaks is the private repository's name (already public knowledge), run ids, digests (public after release anyway), and an unreleased version number in a run title before approval. Today's approval summary carries the private commit SHA and checklist reference. That summary would need a sanitized public form or would stay private.
- **Minimal-disclosure variant (inferred).** Download with a quiet `gh api` script, keep identifiers out of `with:` and run-name, and never enable step debug logging.

**macOS codesign in public (observed + inferred).**

- **Free:** "GitHub Actions usage is free … for public repositories that use standard GitHub-hosted runners" ([billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). `macos-latest` is arm64, and Free allows 5 concurrent macOS jobs ([limits](https://docs.github.com/en/actions/reference/limits)).
- **What it can run:** a public job can download the Darwin archive and run `codesign --verify --deep --strict` plus `--version` and `--help` before approval. That is the check [ADR 0030](https://github.com/secantdev/secant/blob/97a94cd/docs/adr/0030-ship-the-shell-as-a-bun-compiled-single-file-executable.md) requires because Bun's re-signing has regressed twice.
- **What it cannot run:** the full macOS consumer scenarios (`package-smoke.ts`, `release-consumer.ts` and others), because they are source scripts.
- **Why not the private test suite:** running it on public macOS runners would put source-derived test output in public logs. GitHub's [Actions terms](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features) forbid using GitHub-hosted runners for "any other activity unrelated to the production, testing, deployment, or publication of the software project associated with the repository where GitHub Actions are used". They allow "disabling of repositories created to run Actions in a way that violates these Terms". Verifying and publishing the release bytes of the project that repository distributes fits those terms. Using the repository as a free test farm for private source is a risk (inferred).

**Secant today (observed through the read-only API).** Plan `free`, 1 seat. The only ruleset is `noForcePush` (branch, active). The `release` environment has required reviewer `Sandstorm831`, `prevent_self_review: false`, `can_admins_bypass: false`, and deployment policy `v*` (tag). Default workflow permissions are `read`. Each of these protections exists because the repository is public. Making it private on Free leaves only the read-only token default and plain repository secrets.

For release safety, a private repository on Free therefore cannot hold a publishing credential that only an approved job can read. Any repository secret is available to any workflow run on any pushed branch. That is why the approval and the npm credential must live in the public repository, or the release must give up a protected human approval.

## Still unknown

- **Runtimes on 2-vCPU private and third-party runners.** This matters for the dollar figures but not for feasibility. The census used public 4-vCPU runners. Only a private or trial run measures the change.
- **Whether the Windows check runs unchanged on Blacksmith or Namespace Windows images** (temp-drive step, 7 GB RAM, Blacksmith's beta). This matters for the Windows choice and needs a trial run.
- **What a $0 Stop-usage budget blocks when private artifact storage exceeds 500 MB.** This matters: storage will exceed the allowance at any realistic push rate, so either a small storage budget (~$3–5/month at the observed rate, derived) or smaller artifacts is needed. The 90-day pre-M12 artifacts (about 13.5 GiB, expiring January 2027) would also count unless deleted.
- **Sustained push rate.** One post-M12 day is a small sample, and the monthly cost scales linearly with it. Re-measure after a week.
- **GitHub App permission lists for Sengi, GetMac, Ubicloud, WarpBuild, Depot, Cirun and RunsOn Flex,** none of which are published. This matters for the source-access decision and is visible on the install consent screen without buying anything.
- **Namespace's smallest Windows size and post-trial behaviour; WarpBuild's credit amount and expiry; Depot's macOS minute accounting.** These matter only if one of those providers is chosen.
- **Whether the run page UI shows `workflow_dispatch` inputs to signed-in users.** This is minor; keeping private identifiers out of inputs avoids it.
- **Whether every provider works for a private repository on a Free organization.** This is inferred from GitHub's runner-group rules and the absence of any stated plan requirement, not from a provider statement (except RunsOn: "on any GitHub plan (including free plans)").
