# Install Claude Hook Settings in the Scoped `settings.json`, Registered for Startup and Resume

DevFlow installs Claude hook entries into the run-scoped **Scoped provider home** (`$CLAUDE_CONFIG_DIR` = `.devflow/runs/<run-id>/.claude/`, see ADR-0017), pointing them at run-scoped hook scripts under that same directory and cleaning up only DevFlow-owned entries afterward. Hooks are written to **`settings.json`** and the `SessionStart` hook is registered under **two matchers — `startup` and `resume`**. Installation is **idempotent**: re-installing the same command for the same `(event, matcher)` does not append a duplicate.

## Amendment (2026-06-14)

This ADR originally decided to install into project-local **`settings.local.json`**, on the premise that *"Claude Code does not expose a documented scoped provider-home override equivalent to Codex's `CODEX_HOME`."* Both the premise and the decision are now corrected:

- **Premise corrected.** ADR-0017 establishes that Claude *does* honor a scoped provider home via `CLAUDE_CONFIG_DIR`, and DevFlow now runs every Claude managed session under one. There is no global user-settings file to protect — the scoped `settings.json` is itself run-scoped and torn down with the run.
- **Location corrected to `settings.json`.** Verified empirically (Claude v2.1.177, macOS): under a custom `CLAUDE_CONFIG_DIR`, Claude reads user-level hooks from `settings.json` only — `settings.local.json` is **never read** from the config dir (it is a project-local file discovered at `<cwd>/.claude/settings.local.json`). Hooks placed in `settings.local.json` therefore never load, so `SessionStart` never arrives and the session times out. Because the home is scoped and ephemeral, the original "avoid mutating global settings" rationale for choosing `local` no longer applies. Read-merge-write preserves any pre-existing keys; cleanup strips only DevFlow-owned command entries and removes the file only if it was emptied.
- **Startup + resume registration (new).** A `SessionStart` matcher filters on the payload's `source` field (`startup | resume | clear | compact`); the payload carries `source`, never an echoed `matcher`. Registering only `startup` means the hook never fires on `--resume`, so every Claude-hooks **Provider session recovery** would hang on the first-event timeout despite the adapter advertising `supportsResume: true`. DevFlow therefore registers `SessionStart` for **both `startup` and `resume`**. It deliberately does **not** register `clear` or `compact`: those fire mid-session, and a second `session-start` event after the runner has already bootstrapped would reach the phase manager as a spurious mid-turn event. DevFlow needs no clear/compact signal.
- **Idempotent install (new).** The scoped home is per-run and shared by every managed session in the run (grill, PRD, decomposition, each execution iteration), and the hook command is byte-identical across sessions. An unconditional append would accumulate duplicate entries, causing Claude to fire the hook — and deliver duplicate normalized events — N times per turn boundary. Install dedupes on `(event, matcher, command)`; cleanup runs on the success teardown paths (mirroring credential deletion), preserving entries on failure for post-mortem debugging.

Claude JSONL log discovery remains a separate, hook-independent concern.
