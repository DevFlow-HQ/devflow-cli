# Self-Heal node-pty's macOS spawn-helper Executable Bit at Spawn Time

DevFlow's **Control transport** is `node-pty` for every provider (see ADR-0002). On macOS, `node-pty`'s native spawn path is fundamentally different from Linux's: rather than `forkpty()` + `execvp()` in-process (the Linux path), it spawns a separate prebuilt `spawn-helper` binary via `posix_spawn`, and that helper sets up the controlling tty before exec'ing the real provider CLI. The published `node-pty@1.1.0` registry tarball ships `prebuilds/darwin-{arm64,x64}/spawn-helper` with mode `0644` — **no executable bit** — and node-pty's install script only checks that the prebuild directory exists; it never restores the bit. So every clean install on macOS yields a non-executable helper, `posix_spawn` fails with `EACCES`, and node-pty throws `posix_spawnp failed.`, which surfaces as a `ProviderSessionLaunchError` and aborts the **Managed session** before it can start. The failure is macOS-only and provider-agnostic — Linux never execs the helper, and the bug is in the shared transport, not in any adapter (it merely *looked* like a Claude problem because Claude was the provider selected when it first bit).

We self-heal at spawn time. A provider-agnostic `ensureSpawnHelperExecutable` helper runs at the top of `nodePtySpawner.spawn` — the codebase's single `node-pty` boundary and the only module that knows about node-pty's prebuild layout. On `darwin` only, it locates the helper via `require.resolve('node-pty')` + `prebuilds/${platform}-${arch}/spawn-helper` (hoist-proof, and matching the verified on-disk layout), `stat`s it, and `chmod`s the executable bit **only when it is missing**. A healthy or already-fixed install (e.g. a future node-pty that ships the bit correctly) pays one `statSync` and mutates nothing; a missing file is treated as a silent no-op so node-pty can surface its own error. The heal is kept out of `startPtyControlHarness`, which is written against the abstract `PtySpawner` interface and must stay transport-generic — so injecting a fake spawner in tests skips the heal and no real filesystem is touched. The helper takes its `platform`/`arch`/`resolve`/`statSync`/`chmodSync` dependencies as injectable parameters so every branch is unit-testable without a real macOS install.

When the `chmod` itself fails — the realistic case is a root-owned global install or a read-only filesystem, where an unprivileged `chmod` returns `EPERM`/`EROFS` — we fail fast with a plain `Error` carrying a copy-pasteable remediation (`sudo chmod +x <absolute-path>`); the existing `try/catch` in `startPtyControlHarness` wraps it into a `ProviderSessionLaunchError` with the provider id attached. This is a strict improvement over the status quo even where we cannot auto-heal: the user gets the exact fix and a known recovery path (re-running resumes from durable artifacts) instead of a cryptic `posix_spawnp failed.`.

We considered and rejected two alternatives. A `postinstall` `chmod` is defeated by npm hoisting (a dependency's lifecycle script runs with its own cwd, while node-pty is hoisted to the consumer root) and by `--ignore-scripts`, so it would silently not run for the cases that matter — and it does nothing for our primary, intended use as a standalone tool run from a local checkout. Upgrading to `node-pty@1.2.0-beta.x`, whose tarball ships the bit correctly, would fix the root cause but takes a pre-release dependency on the tool's single load-bearing transport. Instead we pin `node-pty` to exactly `1.1.0` (the heal hardcodes its prebuild layout, so upgrades must be deliberate) and add a guard test asserting the resolved helper path exists in the installed node-pty, turning any future layout drift into a loud CI failure rather than a silently dormant heal. When node-pty ships a stable release with the bit fixed, the stat-guard makes the heal dormant automatically, and this workaround can be removed.
